[C] `registry_analysis.cpp` translates baseline lookup `0x2ef724..0x2ef752`, identity/friend lookup `0x2df608..0x2df636` and identity-key construction `0x369e70..0x369f6b`. [I] Names describe observed use; they are not recovered original declarations. [C] Addresses are cheat RVAs and bounds below are half open.

[C] Baseline lookup calls default-inserting map operator `0x2ecc20..0x2ecd56`, dereferences the returned iterator's node and returns `node+0x14`. Its key is exactly four bytes: the integer equality leaf at `0x2d5544..0x2d554d` compares 32-bit values. Hash forwarding reaches `0x2d0ae4 → 0x2d089c → 0x2d7078`, using basis `0xcbf29ce484222325`, multiplier `0x100000001b3` and the four little-endian key bytes.

[C] Identity lookup uses `0x2de574..0x2de6aa`, returning `node+0x30`. Hashing uses the string's stored length and all bytes; equality `0x2d6fd4 → 0x2d1988` compares lengths before comparing bytes. Embedded NULs therefore remain significant. [C] `identity_key_369e70` first rejects an out-of-range player or a nonzero third argument, then reads player `+0x640`, checks that numeric pointer and scans UTF16 at managed object `+0x14` to a zero word. It copies the low byte of every preceding word through `0x2cf7e4..0x2cf7ff`, including a zero low byte from a nonzero word such as `0x0100`. [C] The managed length at `+0x10` is not the scan bound. Empty and rejected inputs yield an empty byte key.

[C] The native find routines `0x2d07d4..0x2d0861` and `0x2de154..0x2de1e1` start at the bucket's last node and walk `node+8` toward its first. Their alternate miss tails are included. An equal key returns before allocation or value initialization. A miss constructs a node, may rehash, repeats the lookup after growth and then calls `0x2d7328..0x2d73cb` to splice the node before the bucket's first node; an empty bucket appends before the list sentinel. Native `node+0` is next and `node+8` is previous.

[C] Baseline node allocation requests 48 bytes through `0x31937c → 0x31a884 → 0x2ebfec → 0x2cb050`. Pair construction reaches `0x2ea4d0..0x2ea50b`: key at node `+0x10`, 24 zero value bytes at `+0x14..+0x2c`. The subsequent `0x2eee78..0x2eee98` calls two identity/no-op constructors and adds no stores. Node tail padding `+0x2c..+0x30` is not initialized by this constructor.

[C] Identity allocation requests 96 bytes through `0x2e28a0 → 0x2e3294 → 0x2de298 → 0x2cb050`. Pair construction reaches `0x2dde50..0x2dde86`: key string at node `+0x10`, mapped value at `+0x30`. `0x2df388..0x2df3ab` initializes an empty 32-byte string in the value, writes a zero WORD at value `+0x20`, a zero DWORD at `+0x24` and a zero BYTE at `+0x28`. The two bytes at `+0x22` and bytes from `+0x29` onward remain allocator contents. These bytes are preserved, rather than attributed zero values. [I] Friend/enemy classification is the DWORD at value `+0x24` in existing entity consumers.

[C] Growth translates the unique-key path in complete rehash bodies `0x319be8..0x319df2` and `0x2e2bac..0x2e2db6`, including their alternate splice tails. The load comparison uses binary32 `(size+1)/bucket_count > maximum_load`. Required count is the ceiling of binary32 `(size+1)/maximum_load`, at least eight. Tables below 512 buckets grow eightfold when sufficient, and the result rounds up to a power of two. Forward traversal moves subsequent colliding nodes before the new bucket's current first node. [C] Fixtures check a fixed collision/rehash order, not only key membership.

## Owned storage adaptation

[I] `OwnedSnapshotAllocator` reserves caller-provided copied bytes and never clears them. `RegistryStore` owns key/hash bookkeeping, bucket count and list order in C++ storage; native map-header and bucket-vector allocation are adapted. Nodes and long key buffers live in the caller's Snapshot and retain native node/value offsets and next/previous links. Payload addresses remain stable across rehash. Keys are immutable after insertion; callers may mutate mapped-value bytes. [I] Sentinel storage is reduced to its two observable links. Long key strings use exact owned capacity rather than native allocator rounding; allocation addresses, heap metadata, deallocation order and native capacity/exception behavior are not claimed identical. [C] None of those differences changes the preserved key comparisons, insertion/rehash order or mapped-value initialization under the documented immutable-key contract.

[I] Exhausted/missing copied storage returns `missing_bytes`; finite name-scan and excessive-table bounds return `analysis_limit`. Native scanning/growth is not attributed these safeguards. Insertion is not transactional: prior arena reservations and constructor stores remain after an analysis failure. [C] No numeric address is executed or dereferenced as a host pointer.
