## Detection implications

[C] These installation paths write function-pointer cells and cheat records; they do not overwrite GameAssembly instruction bytes (`0x2ea956–0x2ea963`, `0x2eaa11–0x2eaa1b`, `0x316444–0x31644c`, `0x3164e8–0x3164ee`). [I] A check restricted to hashing GameAssembly executable pages can therefore pass while dispatch is redirected. [U] This is not a claim that every other component in the delivery chain avoids inline patching.

[I] Pointer-integrity coverage should enumerate MethodInfo `methodPointer` cells and the actual virtual/table dispatch cells, including duplicates and inherited slots, and compare them to a build-specific baseline. Check the resolved destination and any forwarding thunk against GameAssembly and explicitly trusted module/code ranges. Evidence motivating both surfaces: MethodInfo swap `0x2ea960`, class-slot swaps `0x2eaa11`, `0x2eaaad`, `0x316449`, `0x3164eb`.

[I] For suspicious destinations, correlate executable-page provenance with loader records and memory mappings: outside known modules, private/unbacked executable pages, manually mapped PE-shaped regions, or an image without the expected signed file backing. A module-range test alone is weaker than checking the expected target for each slot. [U] The supplied static dump does not establish the live allocation type or file backing of every detour page; those require process memory-map evidence.

[I] Treat legitimate Unity-generated thunks and supported instrumentation as explicit exceptions, then investigate unexpected changes or mixed original/detour slots. Correlate pointer anomalies with the Unity rendering and synthetic-stack evidence in reports 02–03; none of the scene names alone is a reliable verdict.
