## Findings: validation false positives

### Medium — event evidence is not paired with the recorded verification run

[C] [audit.py:85](/home/john/Desktop/cheat_re/source/test_scene/audit.py:85) reads current `events.jsonl` and [audit.py:97](/home/john/Desktop/cheat_re/source/test_scene/audit.py:97) applies semantic assertions to it. The checked record binds executable hashes, PNG captures and entrypoint counters at [audit.py:111](/home/john/Desktop/cheat_re/source/test_scene/audit.py:111), but does not compare a recorded event-log hash. [audit.py:135](/home/john/Desktop/cheat_re/source/test_scene/audit.py:135) merely computes the hash of whatever event file is present now. [verify.py:141](/home/john/Desktop/cheat_re/source/test_scene/verify.py:141) records artifact/capture/entrypoint evidence without an event-log or runtime-log digest.

[I] Consequently, replacing a run's event file with another semantically passing event file can leave all audit checks true while the reported events do not belong to the verified executable/captures. This is an evidence-pairing gap, not evidence that retained files were replaced. Record and compare event/runtime-log hashes in verification; preferably also bind the build-record digest. A hash newly reported by the audit cannot independently establish run provenance.

### Medium — per-capture “submission” assertions measure export/finalization rather than submission

[C] The `submitted_lists` JSON field is serialized from `FrameReport::exported_lists`, at [host.cpp:174](/home/john/Desktop/cheat_re/source/test_scene/host.cpp:174). Those IDs are appended during draw-data export, before submission, at [frame.cpp:316](/home/john/Desktop/cheat_re/source/test_scene/frame.cpp:316). `frame_finalized` is set at [frame.cpp:324](/home/john/Desktop/cheat_re/source/test_scene/frame.cpp:324), also before submission. Neither `FrameReport::result.submitted` nor its status/site is serialized at [host.cpp:141](/home/john/Desktop/cheat_re/source/test_scene/host.cpp:141).

[C] [audit.py:52](/home/john/Desktop/cheat_re/source/test_scene/audit.py:52) checks these exported IDs against the current selection; [audit.py:74](/home/john/Desktop/cheat_re/source/test_scene/audit.py:74) checks finalization/counts/GPU-false. A global positive `FrameLifecycle::recorded_submission` counter is required at [audit.py:99](/home/john/Desktop/cheat_re/source/test_scene/audit.py:99), but it is not associated with each captured frame. The recovered submit controller can return complete with `submitted=false` for an unready mesh or empty viewport/geometry: [unity_backend_analysis.cpp:313](/home/john/Desktop/cheat_re/source/reconstructed/unity_backend_analysis.cpp:313), [unity_backend_analysis.cpp:325](/home/john/Desktop/cheat_re/source/reconstructed/unity_backend_analysis.cpp:325). [scene.cpp:45](/home/john/Desktop/cheat_re/source/test_scene/scene.cpp:45) checks status only.

[I] Thus the per-event audit could accept a finalized/exported capture without a recorded submission, provided another frame supplied the global counter. Current fixed mesh readiness and positive scenario geometry make that specific skip unlikely in this source; it remains a concrete false-positive validation path. Serialize status/site/submitted and require submitted for the expected positive capture stages. Name the existing IDs `exported_lists`, or explicitly document that `submitted_lists` reports export selection. Recording execute success still must not be called GPU execution.
