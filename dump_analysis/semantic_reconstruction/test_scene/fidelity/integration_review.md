## Findings and safe parent actions

### P1 — F1: recovered frame/menu roots are absent from scene coverage

[C] `Scene::frame` is `reset -> menu -> ESP -> host text -> rasterize`; it does not call `replay_unity_frame_2f8574`, `bind_frame_dependencies`, `bind_frame_menu`, or `replay_frame_menu_35d5ac`. The full menu root performs hotkey-window work, language-font handling, notifications, closed-menu branching, text events and `frame_main_menu_35fc8b`: [full menu root](/home/john/Desktop/cheat_re/source/reconstructed/frame_dependencies_main_menu.cpp:866). The main controller registers 21 page entries and drives category/search/window/animation paths: [main controller](/home/john/Desktop/cheat_re/source/reconstructed/frame_dependencies_main_menu.cpp:513). The scene calls only the selected-page dispatcher with one authored page key `0x410100`.

[I] This is a substantial lifecycle gap if the scene is used as evidence of original integration. It is not evidence that the documented narrower owned scene is broken; its README already acknowledges authored page/context scaffolding. Keep a named coverage ledger for the omitted controllers and separate three claims: translated offline, separately fixture-tested, exercised by this scene.

[I] Safe next regression: use the existing **owned** `replay_unity_frame_2f8574` callback harness to record a complete ordered event log and consume explicitly supplied results. Assert setup once/retry, original-before-early-return, changing results across the three disconnected queries, invalid-player worker exclusion with UI continuation, splash/content transition and finalization/submission ordering. Extend [existing frame checks](/home/john/Desktop/cheat_re/source/reconstructed/unity_backend_checks.cpp:205), whose domain effects currently return supplied values. Count these as controller-order tests until actual local menu/draw binders are composed. Never substitute successful no-op callbacks for unimplemented feature behavior and then call it end-to-end coverage.

### P1 — F2: menu changes affect a different frame than in the recovered order

[C] The original content sequence draws overlay/world **before** menu `35d5ac` (`2f8d40`, `2f8d4d`, `2f8d79`). The recovered controller preserves that order: [content dispatch](/home/john/Desktop/cheat_re/source/reconstructed/unity_backend_analysis.cpp:569). The host applies menu changes at [scene.cpp:33](/home/john/Desktop/cheat_re/source/test_scene/scene.cpp:33), writes them back to `Settings` at [menu.cpp:385](/home/john/Desktop/cheat_re/source/test_scene/menu.cpp:385), and draws ESP with those values immediately at [scene.cpp:35](/home/john/Desktop/cheat_re/source/test_scene/scene.cpp:35). The README's “same frame” statement accurately describes the host but does not describe original frame ordering: [README](/home/john/Desktop/cheat_re/source/test_scene/README.md:61).

[I] A menu-triggered edit ordinarily reaches the original earlier world draw on the **next invocation**, assuming the inspected single-threaded sequence and no independent writer. Visual stacking is a separate issue: host rasterization already draws ESP before the menu by numeric list order even though CPU construction order is reversed: [raster order](/home/john/Desktop/cheat_re/source/test_scene/resources.cpp:260).

[I] Safe action: either explicitly retain this as an authored responsiveness adaptation, or render ESP from a start-of-frame settings snapshot while committing menu edits for the following frame. Preserve menu capture cleanup on minimized frames; do not simply move the zero-size return before the menu call. Add a release-frame/next-frame assertion for checkbox, distance and color output, plus a menu-over-ESP overlap assertion. Existing staged captures after multiple input frames do not establish this timing distinction.

### P1 — F3: recovered hex editor is reached, but interactive text input is not wired
